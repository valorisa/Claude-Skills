# Collaborative Technical Peer Review

> Une méthodologie structurée de revue technique collaborative pour produire
> des analyses plus robustes, des documents plus précis et des décisions mieux
> argumentées.

## Présentation

Les projets techniques complexes gagnent rarement en qualité grâce à une
validation immédiate. Ils progressent lorsqu'ils sont soumis à une critique
constructive, argumentée et méthodique.

Cette skill formalise une démarche de revue inspirée de la revue par les pairs
(*peer review*), adaptée aux projets d'ingénierie logicielle, de cybersécurité,
de cryptographie, de documentation technique et d'architecture.

L'objectif n'est pas de rechercher un consensus artificiel, mais d'améliorer
progressivement un travail en confrontant plusieurs analyses, en explicitant les
désaccords et en documentant les décisions retenues.

## Philosophie

Cette méthode repose sur quelques principes simples.

- Les désaccords argumentés sont une source de progrès.
- Toute critique doit être justifiée.
- Toute concession doit être explicite.
- Les ambiguïtés doivent être levées.
- La terminologie doit être cohérente avec les standards du domaine.
- Les différents niveaux de lecture doivent être distingués.

Le résultat attendu n'est pas une victoire dialectique, mais un document plus
solide que chacune des versions intermédiaires.

## À qui s'adresse cette skill

Cette méthodologie est adaptée aux personnes qui produisent ou relisent des
contenus techniques, notamment :

- développeurs ;
- architectes logiciels ;
- ingénieurs sécurité ;
- cryptographes ;
- auteurs de documentation ;
- mainteneurs de projets open source ;
- enseignants ;
- étudiants.

## Cas d'utilisation

La skill peut être utilisée pour relire ou améliorer :

- un README ;
- une spécification technique ;
- une RFC ;
- une ADR (*Architecture Decision Record*) ;
- un dépôt GitHub ;
- une documentation API ;
- un audit de sécurité ;
- un article technique ;
- un billet de blog ;
- une analyse de vulnérabilité ;
- un commentaire technique destiné à un forum ou à une vidéo.

## Ce que fait la skill

La revue suit plusieurs étapes.

1. Analyse du document initial.
2. Identification des erreurs et ambiguïtés.
3. Distinction entre vulgarisation et rigueur académique.
4. Recherche systématique des angles morts.
5. Proposition de corrections argumentées.
6. Consolidation des modifications retenues.
7. Relecture finale avec le regard d'un reviewer indépendant.

Chaque étape vise à renforcer la qualité du document sans sacrifier sa
lisibilité.

## Ce que cette skill ne fait pas

Cette méthodologie ne cherche pas à :

- donner raison à une personne ;
- produire un consensus à tout prix ;
- défendre une position initiale malgré les faits ;
- remplacer les standards ou la littérature scientifique.

Lorsqu'une affirmation est incertaine, cette incertitude est explicitement
mentionnée.

## Principes de revue

Chaque critique doit répondre aux questions suivantes.

- Quel est le problème identifié ?
- Pourquoi est-ce un problème ?
- Quelle référence, quel standard ou quel raisonnement le justifie ?
- Quelle correction est proposée ?
- Quels compromis cette correction introduit-elle ?

Inversement, lorsqu'un point est jugé correct, il est également utile
d'expliquer pourquoi.

## Gestion des désaccords

Les désaccords sont classés en plusieurs catégories.

- erreur factuelle ;
- imprécision terminologique ;
- simplification pédagogique ;
- divergence de modèle ;
- choix éditorial ;
- question encore ouverte.

Cette classification évite de traiter comme des erreurs ce qui relève en
réalité d'un choix de niveau de lecture.

## Niveaux de lecture

Une même explication peut être pertinente pour différents publics.

Cette skill encourage à distinguer explicitement plusieurs niveaux.

### Vulgarisation

Le message principal est correct et compréhensible, même si certains détails
sont simplifiés.

### Ingénierie

Les formulations doivent être suffisamment précises pour guider une
implémentation correcte.

### Rigueur académique

Les définitions, hypothèses et limites doivent être explicites et conformes à
la littérature scientifique.

## Livrables possibles

Selon le contexte, la revue peut aboutir à :

- un commentaire corrigé ;
- un document consolidé ;
- un guide pédagogique ;
- une documentation technique ;
- une page de dépôt GitHub ;
- une spécification ;
- une proposition de correction ;
- une feuille de route documentaire.

## Exemples d'application

Cette méthodologie est particulièrement adaptée à des sujets comme :

- les générateurs aléatoires ;
- la cryptographie ;
- les protocoles réseau ;
- la sécurité des systèmes ;
- les architectures logicielles ;
- les formats de données ;
- les API ;
- les standards industriels.

Elle reste néanmoins suffisamment générique pour être appliquée à la plupart
des domaines techniques.

## Bénéfices

Une revue menée selon cette méthode permet généralement de :

- améliorer la précision technique ;
- réduire les ambiguïtés ;
- distinguer les faits des hypothèses ;
- renforcer la cohérence documentaire ;
- rendre les compromis explicites ;
- produire une documentation durable.

## Conseils d'utilisation

Pour tirer le meilleur parti de cette skill :

- fournissez le document complet lorsque c'est possible ;
- indiquez le public visé ;
- précisez le niveau de rigueur attendu ;
- acceptez que certaines critiques conduisent à revoir des hypothèses
  initiales ;
- documentez les décisions prises.

## Philosophie finale

Une bonne revue technique ne cherche pas à démontrer qu'un auteur avait tort.

Elle cherche à produire un résultat que tous les participants considéreront
comme meilleur que leur première proposition.

La qualité ne naît pas de l'absence de désaccords.

Elle naît de leur résolution argumentée.

Lorsqu'une discussion technique se transforme en une documentation claire,
durable et réutilisable, la revue a pleinement atteint son objectif.
